# TreeChat · 树形 AI 对话

> 本文是一份**功能与流程说明**，面向「想复刻类似功能」的读者：只描述产品**应当提供什么能力、用户如何使用**，不涉及任何本地代码、目录结构或部署细节。把它拿给别人看，对方就能明白「你要实现的是一个什么东西、该怎么用」。

---

## 一、产品定位

TreeChat 是一个把 AI 对话组织成**树**、而不是线性列表的应用。

**它要解决的核心痛点**：在传统的线性对话应用里，对任意一条「回答」继续追问时，新对话总是与当前对话平级、排在后面，把之前的上下文顶上去；想返回某条旧回答只能往前翻历史，很麻烦。

**它的做法**：你可以配置自己的 AI 接口（任何兼容 OpenAI 格式的模型），然后对**任意一条回答**发起追问；这条追问与它的回复会作为该回答的**子节点**挂在它之下，让同一个话题自然长出多条可独立浏览的分支。同时，系统会自动把每个问答整理成「上下文元素」，并通过两阶段机制为每次提问智能挑选相关上下文。

## 二、父子节点机制（核心机制一）

这是 TreeChat 区别于线性对话应用的根本：对话不是一条线，而是一棵树。

### 2.1 一个节点 = 一问一答
树的最小单元是一个「节点」，它对应一条**用户提问 + 一条 AI 回答**。每个节点除了问答正文，还自带元数据：摘要、标签、创建时间、所用模型的记录。

### 2.2 树是怎么长出来的
- **根节点**：一棵对话树从第一个问题开始，它是最顶层的根节点（没有父节点）。
- **子节点**：对任意一条已完成回答点「追问」，新问题和它得到的回答就挂在这条回答**之下**，成为它的**子节点**。
- **分叉**：同一条回答可以被追问**多次**，于是它拥有多个子节点——这些子节点彼此是**同父的平级**关系，各自又能继续向下分叉。
- 如此反复，一个话题会长成一棵可无限生长的对话树，从任意回答分叉都是自然操作。

### 2.3 每个节点在树中的位置由三个属性描述
- **父节点（parent）**：指向它「由哪条回答追问而来」。根节点的父节点为空。
- **深度（depth）**：从根节点往下数的层数。根节点深度为 0，每往下一层深度 +1。
- **同层序号（sibling index）**：在「同一父节点」下的排位。例如父节点下第 3 次追问，序号就是 2（从 0 计）。这个序号按「该父节点当前已有子节点数量」自然分配，保证同层顺序稳定。

### 2.4 节点之间只存在三种关系
- **父子**：一条回答与其追问。
- **同父平级**：两条由同一回答追问出来的回答。
- **无关**：分属不同分支、彼此没有直接的父子或同父关系的两个节点（它们之间也可以被上下文机制跨分支关联，见下一章）。

### 2.5 删除节点的两种方式
删除某个节点时，需要明确它的子树如何处置：
- **丢弃整条子树**：连同该节点及其所有后代一并删除。
- **上提合并**：把该节点的子节点「提升一级」，挂到被删节点的父节点之下，从而保留对话脉络。

## 三、上下文机制（核心机制二）

### 先厘清三个概念
在讲机制前，先明确三个反复出现的词：
- **节点（node）**：就是第二章里的一问一答，是树的最小单元，也是上下文的基本「原料」。
- **元数据（metadata）**：描述一个节点的「摘要信息」，包括摘要、标签、创建时间、所属树、父节点、深度等。**元数据刻意不含完整的问答正文**，体积小，适合被批量检索。
- **上下文（context）**：指「这次提问时，一并喂给模型作参考的其它节点内容」。一段上下文，本质上就是一组被选中的节点（及其正文）。

线性对话里上下文只有「往上这一段」；树形结构让上下文来源变复杂：一条提问既要参考它的**祖先路径**，也可能要参考**同树其它分支**里相关的内容。TreeChat 用「总表 + 每节点子集 + 两阶段引擎」来解决这个问题。

### 3.1 上下文元素总表 与 每节点子集
- **上下文元素总表**：一棵树里的**全部节点的元数据**（每个节点的摘要、标签、时间、所属树、父节点等元数据）构成一张元数据总表。它是全树上下文的统一检索面。
- **每节点上下文子集**：每个节点都记录「自己生成问答时所实际使用的节点的 ID 列表」，它是总表的一个子集。
- 区分这两个概念的意义在于：总表负责「能被检索到什么」，每节点子集负责「这次到底看了哪些」，后者让每一次回答的上下文来源**可解释、可复用、可手动覆盖**。

### 3.2 两类上下文：直接上下文 与 跨分支上下文
- **直接上下文（direct）**：指从根到当前节点父级的**整条祖先路径上的节点**。它是这条回答之所以成立的「来龙去脉」，因此被**强制包含**，不依赖模型判断。
- **跨分支上下文（cross）**：同一棵树里、但不在当前祖先路径上的其它节点（即「别的支线」里可能相关的历史问答）。是否纳入由模型检索决定。

### 3.3 两阶段上下文引擎
每次提问时，系统分两步决定「带哪些历史上下文去问」：

**阶段一 · 检索（挑相关）**

这一阶段的目标只有一句话：**从整棵树里，找出和「这次新提问」相关、但不在当前祖先路径上的节点**（也就是潜在的「跨分支上下文」）。

具体分几步：

1. **排除已经确定要带的节点**。祖先路径上的节点（即从根到当前父级的整条链）是「直接上下文」，必定会被带上，不需要检索，所以先从候选里去掉。剩下的候选 = 全树里「其它分支」的节点。
2. **构建一份轻量元数据索引**。把每个候选节点压缩成一条「索引记录」——只有 id、深度、标签、摘要，**不含完整问答正文**。之所以只发元数据，是因为正文太长会瞬间占满模型的上下文窗口；标签和摘要足以让模型判断「这个节点跟新提问是否相关」。
3. **离线预筛（控制发给模型的量）**。如果树很大，元数据索引本身也会很长。所以在交给模型之前，先用关键词规则快速打分：和提问**共享标签**的加分、摘要里**包含提问词条**的加分。优先保留命中项，再按一定比例补回一些未命中项，既控制 token 又保留召回广度（不至于漏掉潜在相关项）。祖先路径在预筛中始终保留（尽管它们本就不在候选里）。
4. **交给模型挑选**。把三样东西一起发给模型：
   - 这次的**新提问**；
   - **祖先路径的 ID**（告诉模型「这些已经确定会作为背景，请不要重复选」）；
   - **预筛后的元数据索引**（让模型从中挑选）。
   模型从索引里挑出相关节点的 ID，并给出**选择理由**。
5. **得到跨分支召回**。模型挑出来的节点本来就是「其它分支」的候选，于是它们自然成为「跨分支上下文」的来源，交给阶段二组装。
6. **失败回退**。如果这次检索调用失败（比如模型接口不可用），就跳过检索，回退为「只用直接上下文（祖先路径）」，对话照样能继续，只是失去了跨分支召回能力。

**阶段二 · 组装（控预算）**
- 把「直接上下文（强制）」与「跨分支召回」按 token 预算组装成实际发给模型的提示词。
- **直接上下文超预算时降级**：当祖先路径总 token 超过预算的约 60%，仅保留最近 5 个节点的完整正文，更早的节点用其**摘要**替代，避免把整条长路径塞爆上下文。
- **跨分支按序裁剪**：在剩余预算内，把跨分支节点依次加入；超出预算即停止。
- 最终发给模型的是「直接上下文 + 跨分支上下文 + 本次用户提问」。

### 3.4 元数据随回答一起产出
每条回答生成时，模型在给出正文的同时，顺带产出该节点的**摘要**与**标签**（不额外单独调用）。摘要和标签正是阶段一检索所依赖的元数据，从而形成「越用越能被检索」的闭环。

### 3.5 上下文来源全程留痕（透明与可控）
- 每个节点落库时记录一份「上下文轨迹」：本次用到的直接上下文 ID 列表、跨分支上下文 ID 列表、以及模型给出的选择理由。
- 前端据此在每张回答卡片展示「本次回答用了哪些上下文、为什么选它们」，并可编辑标签。
- **手动覆盖**：用户可在任意节点手动勾选 / 追加其它节点作为上下文，点「用所选上下文重生成」——此时完全绕开阶段一检索，所选节点若在祖先路径内归入直接上下文、否则归入跨分支上下文，再走阶段二组装。

## 四、功能清单

### 1. 可配置自有 AI 接口
- 不绑定某家模型，通过 OpenAI 兼容接口接入自有 Key（DeepSeek / OpenAI / Claude 等均可）。
- 支持保存**多套接口方案**，每套包含名称、地址、Key、模型；可随时切换启用其中一套。
- 提供「模拟模式」：不发起真实请求、直接返回示例回答，便于在没有 Key 时先体验完整交互。
- 每条消息可单独选择使用的模型。

### 2. 树形对话
- 在任意节点点击「追问」，输入子问题，提交后生成该节点的**子节点**，并自动跳转到下一层。
- 对话树可无限生长，从任意回答分叉都是自然操作（详见第二章）。

### 3. 节点上下文元素自动整理
每个回答完成后，系统自动为它生成：
- **摘要**：对这条问答内容的概括文本；
- **标签**：用于检索与归类的关键词；
- **关系与时间元数据**：父节点、所属树、创建时间等。

### 4. 两阶段上下文引擎
见第三章：阶段一跨分支检索 + 阶段二按 token 预算组装，含失败回退、祖先路径降级、手动覆盖与来源留痕。

### 5. 层级分页导航
- **当前层**：完整展示该层所有平级节点（同父的问答卡片）。
- **上一层 / 下一层**：以单行简介条呈现（上一层的父节点、下一层各节点的子节点），点击可穿梭。
- **面包屑**：从根到当前节点的路径，可快速回跳任意祖先层。

### 6. 树视图
- 提供轻量的整树结构视图，点任意节点即跳到其所在层，便于跨分支跳转。

### 7. 回答渲染与操作
- AI 回答按 Markdown 渲染，代码块带语法高亮。
- 每条用户问题与 AI 回答、每个代码块均可一键复制。

### 8. 全局跨树搜索
- 按关键词搜索所有树的所有节点（问题 / 回答 / 摘要 / 标签），点结果直接跳转到对应节点。

### 9. 对话树管理
- 新建、重命名、整树删除（级联清除其全部节点，需确认）。
- **导入 / 导出**：单棵树可导出为 JSON（完整数据）或 Markdown（按层级缩进的问答）；导入时重建为新树，不与原树冲突。

### 10. 探索模式（临时分叉）
- 对某回答发起追问时可标记为「探索模式」，该分叉为临时节点，不影响主路径，可单独删除。

### 11. 手动上下文覆盖
- 在任意节点手动勾选 / 追加其它节点作为上下文，点「用所选上下文重生成」，完全绕开自动检索（详见 3.5）。

### 12. 上下文来源透明度面板
- 每张回答卡片底部展示本次回答的上下文来源（直接 / 跨分支）、模型选择该上下文的**理由**，以及可编辑的标签。

### 13. 节点删除
- 删除某个节点时，可选择「丢弃其整条子树」或「把子节点上提合并」到父层（详见 2.5）。

## 五、用户工作流程

### 准备
- 配置一套或多套 AI 接口方案（或在无 Key 时用模拟模式），选定当前启用的方案与默认模型。

### 新建并开启对话
- 在侧边栏新建一棵对话树。
- 在根节点输入问题并发送，AI 流式返回回答，生成第一个根节点。

### 追问答疑（构建分支）
- 对任意一条已完成的回答点「追问」，输入子问题（可选探索模式），提交后形成该回答的**子节点**，视图自动跳到下一层。
- 如此反复，同一话题逐渐长出一棵可独立浏览的对话树。

### 在树中穿梭
- 用当前层、上一层 / 下一层简介条、面包屑、树视图，在任意层级与分支间浏览。

### 查看与复用上下文
- 每张卡片底部可查看「本次回答用了哪些上下文、为什么选它们」。
- 需要更精准控制时，手动勾选上下文并重生成；或依赖系统自动的两阶段上下文挑选。

### 检索、整理与导出
- 用全局搜索快速定位任意历史节点。
- 重命名树、删除整树，或把有价值的树导出为 JSON / Markdown 留存，亦可导入复用。

## 六、设计动机（为什么这么设计）

- **为什么用树而不是线**：线性应用里，对旧回答的追问会把之前内容顶上去，返回旧回答要靠翻历史；树形让「从任意回答分叉」成为一等公民（父子节点机制见第二章）。
- **为什么要有上下文元素总表 + 每节点子集**：总表让全树上下文可被统一检索；每节点子集保留「这次到底看了哪些」，既支撑跨分支召回，也让上下文来源可解释、可复用、可手动覆盖（见 3.1）。
- **为什么分两阶段选上下文**：先让模型从总表「挑相关」（跨分支召回），再按预算「组装实际提示词」（祖先路径强制 + token 预算裁剪 + 长路径降级），兼顾相关性与可控性，并把选择理由透明呈现给用户（见 3.2–3.3）。
